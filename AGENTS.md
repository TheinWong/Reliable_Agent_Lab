# AGENTS.md — Reliable Agent Lab

## Mission
Build an open-source, production-oriented multi-agent tool-using system that demonstrates Agent Engineering and Backend Engineering. The first validation domain is reproducible diagnosis and recovery of a small Spring Boot microservice system.

The project should showcase:
- LangGraph multi-agent orchestration;
- supervisor + specialist agents;
- MCP tool boundaries;
- FastAPI + asyncio + SSE;
- structured state and outputs;
- human approval for risky actions;
- retry / replan / checkpoint / resume / idempotency;
- OpenTelemetry-based observability;
- deterministic fault scenarios and regression evaluation.

The SRE/incident domain is a validation environment, not the project's identity.

## Primary architecture constraints
- Python 3.12 for agent services.
- LangGraph is the only primary agent orchestration framework.
- Do not add CrewAI, AutoGen, PydanticAI, OpenAI Agents SDK, or Semantic Kernel as a second orchestration framework without explicit user approval.
- MCP is the boundary between agent runtime and externally integrated tools where practical.
- Java 21 + Spring Boot is used for the demo microservice environment.
- PostgreSQL, MySQL, Redis, Prometheus, OpenTelemetry and Jaeger may be used according to the architecture docs.
- Use remote LLM APIs. Do not make local LLM hosting a project requirement.

## Multi-agent design constraints
Target roles are:
1. Supervisor Agent
2. Metrics Agent
3. Logs Agent
4. Trace Agent
5. Remediation Agent
6. Verifier Agent

Specialist agents must have narrow context and narrow tool permissions.
Read-only investigation agents must not receive mutating operations tools.
Planning and execution must remain separable.
Verification must be independent of the remediation agent's self-assessment.
Parallel investigation should be used when tasks are independent and evidence supports it.

## Safety and reliability
- Never provide unrestricted shell execution to an LLM-facing tool.
- Never allow arbitrary mutating SQL generated by an LLM.
- Mutating tools require risk classification.
- High-risk actions require human approval.
- Retried side effects must be idempotent or protected by an idempotency mechanism.
- A tool returning success does not mean the incident is resolved; verify system state independently.
- Every external call needs explicit timeout/error behavior.
- Bound agent loops by steps, time, or budget.

## Engineering behavior
Prefer explicit, testable behavior over framework magic.
Keep important behavior visible in state, graphs, tool contracts, policies, tests, traces and docs.
Do not add abstractions just to look sophisticated.
Do not add dependencies without a concrete need.

## Implementation autonomy
Codex is expected to implement the project with high autonomy.
It may make normal local implementation choices consistent with the project docs.
It should not stop for minor naming, formatting, library patch-version, or boilerplate decisions.

Stop and ask only when:
- credentials or an external service are required and no supported fallback exists;
- a destructive or irreversible remote action is necessary;
- the requested architecture is internally contradictory;
- an acceptance criterion cannot be met with available resources;
- a decision would materially change the project's public scope or core architecture.

If blocked, implement the strongest local/mock alternative, document the blocker, and keep unrelated work moving.
